## 🔧 Fixed in this pass

1. **Default & fallback selection was incomplete.** The old text described only "active provider + one operator fallback" and a from-env Claude-primary/OpenAI-fallback path. Current `getLlmClient()` (`llm.server.ts:471-574`) has two more branches the doc didn't mention: a per-shop override that wins outright, and cost-ranked routing gated behind `AI_COST_ROUTING_ENABLED` (default off, confirmed via `env.server.ts:219-220`) that builds a cheapest-first chain via `getCostRankedActiveProviders()`. Rewrote the section as the actual four-branch resolution order and clarified that `FallbackLlmClient` is provider-agnostic — "Claude primary, OpenAI fallback" is only literally true on the env-key path.
2. **"Auto-reprobe" 20-second polling claim is stale.** The doc described an automatic background poll of `/internal/ai-assistant/probe` every 20 seconds while chat is blocked. No `setInterval`/`setTimeout`-based auto-poll exists in `apps/web/app/routes/internal.ai-assistant.tsx` as of this commit — searched the whole file for `setInterval`, `setTimeout`, and poll-adjacent identifiers and found only a manual "Recheck" button (`recheckTargets()`) plus ordinary Remix loader revalidation. Renamed the section "Target health probing", described the real (manual + revalidation-driven) behavior, and left an explicit correction note rather than silently dropping the old claim.
3. **"Safe target URLs" allowlist scope claim was wrong.** The doc said `INTERNAL_AI_ALLOW_HOSTS`-listed hosts "bypass the localhost/link-local/metadata checks" and are "accepted for both `http:` and `https:`". Traced the actual call: `internal-assistant.server.ts`'s `assertSafeTargetUrl` wrapper passes the allowlist only as `allowedHttpHostnames` into the shared `packages/network-security/src/ssrf.ts` `assertSafeTargetUrl`, whose `isExplicitlyAllowedLocalHttp()` only consults that option when `url.protocol === 'http:'` (`ssrf.ts:117-130, 142`). An `https://` request to an allowlisted-but-private-resolving hostname still goes through `assertMetadataHostname` + full IP-range checks. Also discovered the shared module's real IP blocklist is far broader than "link-local + specific metadata hosts" — it blocks the standard RFC1918 ranges, loopback, CGNAT, several IETF-reserved IPv4 blocks, and the IPv6 private/reserved equivalents (`ssrf.ts:42-81`). Rewrote the section to describe the real scope and flagged the old claim as a correction so it isn't silently re-introduced.
4. **Local-triage-llm system was entirely undocumented.** Per the `local-triage-llm` memory (flagged "uncommitted" at its writing), confirmed `apps/web/app/services/support/triage.server.ts` is real and committed: local-first `qwen3.5:9b` via Ollama with `think: false` + strict JSON `format` (mandatory, not optional — the file's own comment cites a measured ~3,400 thinking tokens vs. 75 output tokens on this model as the reason), `AppSettings.supportTriageMode` (`local | cloud`, default `local`) cloud toggle on the same `/internal/ai-providers` page as the other provider settings, and `SUPPORT_TRIAGE_*` env overrides that win over the DB toggle. This is a **separate** system from the internal prompt router (which routes module-generation context, not support tickets) — the two were previously conflated by the task brief's phrasing. Added a new `## Support ticket triage` section and a matching row in the "Module generation vs internal" product-split table at the top.
5. **OpenAI reasoning-model token headroom was undocumented.** `openai-responses.client.server.ts:47-58` adds a `REASONING_HEADROOM` of 6000 tokens on top of the caller's budget for `gpt-5*`/`o1`/`o3`/`o4*` models specifically, because those models spend output tokens on hidden reasoning before the visible JSON and the API's `max_output_tokens` cap covers both combined. Added this to the "Token limits per call type" section since it's a real, non-obvious behavior a reader tuning token budgets for a reasoning model would need.
6. **Stub-fallback ambiguity (drift-ledger row) addressed directly in the doc.** The existing drift-ledger row "AI provider fallback behavior is clearly documented" flagged that `StubLlmClient` exists but production throws `AiProviderNotConfiguredError`, and docs "can be misread." Confirmed `StubLlmClient` (`llm.server.ts:122`) is only ever constructed by `evals.server.ts`/`tournament.server.ts`, never by `getLlmClient()`'s production path. Added an explicit "no production stub fallback" pitfall bullet so this can't be misread going forward; see Drift-ledger rows closed by this pass.
7. **Module System v2 cross-link redirected.** `## 2026-06-14 — Module-generation uplift` pointed at `./archive/module-system-v2.md` (correct at the time, since Task 1 archived it, but that content is now live in `docs/generation.md` §4 per Task 4). Repointed to `generation.md` §4.
